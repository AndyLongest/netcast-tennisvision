# 开源网球视觉方案速度调研

## 结论摘要

Netcast TennisVision 当前的主要问题不是某一个神经网络完全不可用，而是完整管线以
多个串行阶段重复读取视频，并且在报告数据已经生成后，仍要等待全分辨率标注视频编码
完成。最新 `deemo3` 实测为：200.32 秒视频，从任务建立到成片完成 1060 秒；扣除
81 秒人工确认等待后，自动计算 979 秒，即视频时长的 4.89 倍。

公开资料中，能够直接比较的速度数据主要来自“球检测模型”，而不是完整网球产品。
这些模型在各自测试硬件上的速度大多为 35–150 FPS；真正公开完整端到端耗时的老牌
开源 Tennis Tracking 项目反而需要 16 分钟处理 15 秒视频。换言之，市场上常见的
“实时”数字和我们的 17 分 40 秒不是同一统计口径。

尽管如此，本次比较足以证明当前工程仍有很大的无损提速空间：仅仅让结构化报告先于
标注成片交付，`deemo3` 就可提前约 6 分 10 秒呈现；使用统一低分辨率推理表面、硬件
视频编解码以及单次解码多模型消费，有机会进一步把服务器端报告时间压到接近视频时长。
这应通过同一批视频做端到端 A/B 回归验证，而不能用论文模型 FPS 直接许诺产品速度。

## 1. 比较口径

公开项目的“速度”至少有五种不同含义：

1. 单次张量前向传播，不含视频读取、缩放和后处理；
2. 球模型推理，包含部分数据加载，但不含人物、球场和事件；
3. 在线预览，忙时允许丢帧；
4. 离线逐帧分析，不丢输入帧；
5. 从上传到标注视频写完的完整墙钟时间。

Netcast TennisVision 当前属于第 5 类，并且包含球场确认、人物检测、球员 ReID、球轨迹
关联、击球/落地竞争判定、三维报告和全分辨率标注视频。除非开源项目披露相同范围，
其 FPS 只能说明某个组件的上限，不能当作端到端耗时。

## 2. `deemo3` 本地实测基线

测试机器：NVIDIA GeForce RTX 3050 Ti Laptop GPU（4GB），AMD Ryzen 7 6800H。

输入视频：2880×1620，13.8727 FPS，2779 帧，时长 200.32 秒。

| 阶段 | 墙钟时间 | 说明 |
|---|---:|---|
| 上传后自动球场预处理 | 约 135 秒 | 生成确认画面 |
| 人工确认等待 | 约 81 秒 | 不属于计算耗时 |
| RacketVision 候选生成 | 约 176 秒 | 日志报告模型吞吐 20.9 FPS；文件时间还包含解码/批处理开销 |
| Pass A 其余部分 | 约 269 秒 | 人物检测、帧级元数据与缓存写入 |
| ReID、轨迹、事件和报告 | 约 29 秒 | 输出 JSON 与交互式报告 |
| 2880×1620 标注视频渲染 | 约 370 秒 | 7.51 FPS，是最大的单项等待 |
| 总计 | 1060 秒 | 17 分 40 秒 |
| 扣除人工等待 | 979 秒 | 16 分 19 秒，4.89×视频时长 |

结构化报告在 16:19:11 已经写出，标注视频在 16:25:21 才完成。因此，当前把“报告可看”
绑定到“成片完成”，额外增加了 370 秒用户可见等待，占总耗时约 35%。

## 3. 开源项目与论文公布的速度

### 3.1 WASB-SBDT：当前最有价值的直接基准

WASB-SBDT 是 BMVC 2023 发布的通用体育小球检测与跟踪基线，官方仓库采用 MIT
许可证，并公开数据、代码和权重。论文将所有模型输入统一到 512×288、三帧时序，
测试批量为 8，实验服务器配有 4 张 V100；论文没有明确说明表中推理是否独占一张卡，
因此不能把数字直接外推到单张 3050 Ti。[1][2]

论文在网球数据集上公布：

| 球模型 | 网球 FPS | 处理 `deemo3` 2779 帧的理论模型时间 | 网球 F1 / AP |
|---|---:|---:|---:|
| DeepBall | 52.1 | 53.3 秒 | 47.4 / 47.0 |
| DeepBall-Large | 47.7 | 58.3 秒 | 46.7 / 35.1 |
| BallSeg | 62.7 | 44.3 秒 | 71.7 / 56.8 |
| TrackNetV2 | 55.3 | 50.3 秒 | 89.4 / 80.6 |
| ResTrackNetV2 | 59.0 | 47.1 秒 | 90.3 / 81.7 |
| MonoTrack | 64.1 | 43.4 秒 | 92.1 / 87.3 |
| WASB，Step=3 | 58.2 | 47.7 秒 | 94.0 / 91.0 |
| WASB，Step=1 | 35.2 | 78.9 秒 | 95.6 / 94.2 |

这里的“理论模型时间”只是用帧数除以论文 FPS，未包含原视频解码、人物识别、ReID、
球场、事件分析与输出视频编码。WASB Step=1 精度更好但速度更慢；Step=3 利用步长提高
吞吐，仍然不是“跳过三分之二输入帧”的简单丢帧逻辑。[2]

### 3.2 GridTrackNet：极高吞吐，但不包含视频前后处理

GridTrackNet 使用 768×432 输入和五帧到五帧的多输入多输出设计。论文实测：RTX 3080
上含 TensorFlow 数据加载开销为 149.9 FPS，10 核 M1 Pro 为 101.1 FPS；对应处理
2779 帧约 18.5 秒和 27.5 秒。论文明确说明数字不包含从视频提取帧和预处理。[3]

相同实验中，TrackNetV2 为 RTX 3080 上 96.0 FPS、M1 Pro 上 33.5 FPS。GridTrackNet
测试集 F1 为 95.3%，TrackNetV2 为 93.5%；但该测试集、容差和我们的 RacketVision
回归集合不同，不能用这些百分比宣称替换模型后一定更准。[3]

GridTrackNet 最值得借鉴的不是直接换权重，而是其多输入多输出设计：一次推理产生多帧
结果，减少重复卷积和框架调用开销。

### 3.3 AtomGradient/Swing：手机实时原型，不是完整 SwingVision 产品

这个只有少量社区关注的 iOS 开源原型自称在 iPhone 15 Pro Max 上完全端侧运行：
WASB 球追踪约 3–5ms、Apple Vision 姿态约 2–3ms、球场检测约 5–8ms（每 10 帧一次）、
帧预处理约 2ms，总管线约 10–15ms并以约 30 FPS 显示。[4]

它把画面缩放到 512×288，球场只每 10 帧运行一次，并设置“同一时刻只处理一帧；繁忙
时丢弃后续帧”的背压机制。它展示球、30 帧轨迹、人体骨架和球场线，但没有与本项目
等价的球员 ReID、完整落点审核、三维重建或离线全帧成片。因此它证明了轻量端侧预览
可行，不能证明我们的完整分析可以在手机上 10–15ms 完成。[4]

### 3.4 RacketVision 与 Good-Tennis：功能接近，但没有公布可靠耗时

RacketVision 官方项目公开 BallTrack、RacketPose 和 TrajPred 三阶段以及评测精度，
没有在论文或 README 中公布 FPS。其 BallTrack 是我们现有公开权重来源，因此不能用
“官方演示很流畅”反推端到端处理速度。[5][6]

Good-Tennis 支持 YOLO 球/人物检测、球场映射、回合、落点、小地图与标注视频，并提供
`--performance-stats` 参数，但 README 没有给出任何硬件上的实测时间。项目建议为了
实时预览把人物检测间隔设为 2 或 3；这会改变逐帧人物证据，不符合我们当前“未经回归
不得牺牲准确率”的上线要求。[7]

### 3.5 ArtLabss/tennis-tracking：少数公布完整耗时的项目

ArtLabss 的单目开源 HawkEye 同时运行 TrackNet、人物检测、球场、可选小地图和落点。
README 明确写明：15 秒、6.1MB 的视频需要约 16 分钟处理，即约 64 倍视频时长；早期
版本甚至需要 28 分钟。[8]

这套工程较旧，不能代表现代 GPU 管线，但它说明完整网球分析与单模型 FPS 是两回事。
按“耗时/视频时长”衡量，我们的 `deemo3` 自动计算为 4.89×，明显快于该项目，却仍未
达到可接受的消费级服务体验。

### 3.6 TTNet：相邻运动的多任务架构证据

TTNet 面向乒乓球，不应当直接移植为网球模型；但它在一个网络中联合预测球位置、反弹/
触网事件和语义分割。论文报告在单张消费级 GPU 上每个输入张量少于 6ms，并具备处理
120 FPS 降采样全高清视频的能力。[9]

它说明长期最优架构可能不是把球、人物、球场、事件依次串行堆叠，而是共享特征或至少
并行执行独立视觉分支。其数据域、摄像机和球尺寸与网球不同，速度只能作为设计证据，
不能作为 Netcast 的性能承诺。

## 4. 为什么我们的 17 分 40 秒不能用“换一个 100 FPS 模型”解决

即使把 `deemo3` 的球模型时间从 176 秒降到 GridTrackNet 理论值 20–30 秒，当前流程
仍有大约 804 秒花在球模型之外。主要问题是：

- 2880×1620 每帧约 467 万像素，是 1280×720 的 5.06 倍；检测模型最终仍会缩放输入，
  但 Python/OpenCV 解码、复制、绘制和编码持续承担原始像素成本。
- 球检测和人物 Pass A 串行执行，并多次经过视频帧。
- 标注视频使用 CPU/OpenCV 风格的全分辨率逐帧绘制与编码，`deemo3` 只有 7.51 FPS。
- 球场在固定机位下最终只使用一个标定结果，但确认前仍进行较重的多帧候选搜索。
- 报告数据已经生成后，接口仍等待标注成片完成才宣布任务完成。
- 论文常用 FP16、TensorRT/CoreML、固定低分辨率张量和预加载批次；当前桌面管线仍有
  大量 Python 对象、Notebook 编排、磁盘缓存与格式转换开销。

## 5. 可直接借鉴的优化，按准确率风险分级

### A 级：不改变识别输入和决策，优先实施

1. **报告与成片解耦。** `scene3d.json` 和结构化落点完成后立即让前端进入报告；标注视频
   继续作为后台产物。按 `deemo3` 实测可把用户首次看到报告提前约 370 秒。
2. **硬件视频解码和编码。** 使用 FFmpeg NVDEC/NVENC，避免 Python 逐帧软件编码成为
   高分辨率瓶颈；需做逐帧数、时间戳、色彩和音频同步校验。
3. **只解码一次，多消费者共享帧。** 球模型、人物模型和预览采样从有界队列消费相同的
   解码帧，减少重复读取和颜色转换。
4. **推理与渲染并行。** 当离线轨迹尚需全局平滑时，最终绘制必须等待轨迹完成，但视频
   解码准备、音频分析和独立模型仍可重叠。
5. **完整阶段计时。** 把 decode、resize、host-to-device、model、postprocess、ReID、
   events、draw、encode 分别记录，禁止只展示神经网络 FPS。

### B 级：理论上保持坐标精度，但必须做视频回归

1. **统一推理表面。** 原视频只用于最终显示；球和人物模型统一在固定 720p 或模型原生
   尺寸上工作，再把坐标映射回原视频。RacketVision/WASB 本身已经在 512×288 工作，
   没有必要让其外围逻辑反复持有 2880×1620 数组。
2. **导出 ONNX/TensorRT FP16。** 先逐帧比较候选坐标和置信度，再比较完整轨迹与落点；
   任何候选变化都不能被称为“无损”。
3. **人物检测改成检测+跟踪。** 检测器按经过验证的间隔运行，中间帧由跟踪器输出带不确定
   度的位置；Good-Tennis、RTMLib 和 ByteTrack 都采用类似的检测稀疏化思想。[7][10]
4. **按视频指纹缓存固定球场。** 用户确认后的四角和变换矩阵直接复用，不重新搜索。

### C 级：潜在收益最大，属于模型路线实验

1. A/B 测试 WASB、GridTrackNet 与现有 MS-TrackNetV3；必须在 `demo`、`demo_cut`、
   `demo_colla`、`deemo1`、`deemo3` 和已记录问题时刻上比较真实观测、误检、断轨与落点。
2. 探索多输入多输出推理，让一次网络调用产生连续多帧球位置。
3. 长期训练共享视觉骨干的多任务模型，同时输出球、人物/球拍和接触事件，减少重复特征
   提取；TTNet 证明了该方向的工程潜力，但网球需要自己的训练数据。[9]

## 6. 建议目标与验收方法

不能直接承诺论文中的 100 FPS，但可以为服务器版设立分阶段目标：

| 里程碑 | 用户可见目标 | 准确率约束 |
|---|---|---|
| M1 | 报告先于成片，`deemo3` 至少提前 6 分钟可看 | JSON、落点、归属完全一致 |
| M2 | 同一 3050 Ti 上，结构化报告控制在 ≤2×视频时长 | 冻结测试集所有关键事件不退化 |
| M3 | 服务器推理优化后，结构化报告接近或快于 1×视频时长 | 新视频人工抽检与基线指标双通过 |
| M4 | 标注成片 ≤1.5×视频时长，且不阻塞报告 | 帧数、音频、时间戳严格一致 |

每次优化应在完全相同输入上记录：上传结束时间、球场确认等待、报告可用时间、成片完成
时间、GPU 利用率、显存、各模型 FPS、真实球观测数、轨迹覆盖、击球数、落点数、落点
区域及球员归属。速度提升如果改变关键事件结果，应回退或作为实验分支保留。

## 7. 最终判断

开源证据不支持“所有同类完整产品都能实时”的说法，因为大多数仓库根本没有公布端到端
时间；但它明确支持以下判断：

- 专用球模型达到 30–150 FPS 是现实的；我们当前 20.9 FPS 仍有模型部署优化空间。
- 我们 17 分 40 秒中的大部分并非球模型本身，首先应优化工程管线。
- 立即解耦报告和成片是收益最高、准确率风险最低的改动。
- 服务器端使用固定低分辨率推理、硬件编解码、一次解码和并行分支，是最符合成熟开源
  方案的路线。
- 手机实时原型依靠低分辨率、CoreML/ANE、背压丢帧和精简功能；不能用来证明当前完整
  算法可以原样纯端侧部署。

## 8. 本轮安全优化实测（2026-09-14）

本轮只接收通过完整回归、不会改变生产事件结果的改动：

- 固定机位的已确认球场通过 ORB + RANSAC 做视觉身份核验后复用。`deemo3` 的完整多帧
  球场搜索约 119.3s，复用路径约 8.3s；单次身份核验 1.19s。四角不做二次拟合，最终
  `scene3d.json` SHA-256 与优化前完全一致。
- RacketVision 重叠四帧窗口不再重复转换同一张图。`demo` 的模型循环从 23.2 FPS 提升到
  24.2 FPS（约 4.3%），候选存在性、坐标和置信度逐项完全一致。
- CPU 预取下一批输入并与当前 GPU 推理重叠后，`demo` 的球模型循环从 23.6 FPS 提升到
  33.2 FPS；包含固定准备开销的整段球阶段从 83.0s 降到 62.6s（缩短 24.6%）。1,737
  帧候选逐项完全一致，可用 `TENNISVISION_RACKETVISION_PREFETCH=0` 立即回退。
- 人物每两帧检测一次虽使该分支明显加速，但 `demo` 的击球事件由 35 降至 33；不进入
  生产默认值。
- 人物 TensorRT FP16 在 RTX 3050 Ti 上仅由约 40.5 FPS 提升到 41.5 FPS，并改变下游
  事件；相关运行时、导出模型和生产接线已撤销。

因此目前还不能诚实地称为固定延迟直播：720p 人物分支、球模型循环和成片渲染都已经
分别超过 30 FPS，但这些阶段仍然串行执行，球阶段包含固定准备开销后约为 27.8 FPS。
下一阶段应建立一次解码、GPU 常驻、分支并行的流式服务；任何候选变化仍须通过完整
落点回归。

一次隔离全部球、人物 Pass A 和音频缓存的 `deemo3` 实测显示：在保留已验证固定机位
档案的正常使用场景下，报告在 484.09s（8分04秒）可用，原分辨率标注成片在 753.19s
（12分33秒）完成，其中后台渲染为 269s。结果仍为 782 个轨迹帧、8 个落点和4个击球，
`scene3d.json` 校验值与生产基线完全一致。相较旧版17分40秒等待全部结束，总成片缩短
约5分07秒（29.0%），用户看到报告的等待缩短约9分36秒（54.3%）。
