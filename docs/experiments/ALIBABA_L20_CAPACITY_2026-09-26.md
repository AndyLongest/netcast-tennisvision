# 阿里云 L20 直播并发短测（2026-09-26）

## 结论

在本次**深圳 `ecs.gn8is.2xlarge` 整机**配置与当前识别程序下，3 路和 5 路 1080p/30fps 直播均发生明显的输入帧队列丢弃，不满足保留每帧的直播分析要求。3 路已失败，因此不能把此规格标为「稳定承载 3–5 路」。本次未测 1、2、4 路，无法给出可靠的最大路数。

## 环境与方法

- 阿里云深圳可用区 D，`ecs.gn8is.2xlarge`：1 × NVIDIA L20，显存 46,068 MiB；8 vCPU、64 GiB 内存；100 GiB ESSD 系统盘。
- 从当前代码包启动**每路独立 Python 分析进程**。FFmpeg 将同一段 1080p、30 fps 高视角网球视频按实时速度分别推到业务 ZLM 的 RTMP 地址，再由分析进程订阅；包括球检测、跟踪、姿态和现有直播逻辑。
- 每组正式采样约 45 秒。`timed_out=true` 是测试程序到达预设采样截止时间后主动结束；采样末尾所有分析进程仍处于 `running`，不是服务崩溃。
- `dropped_frames` 是直播输入队列已满时主动丢弃的帧数；下表丢帧率以 `ingested_frames` 为分母。GPU 利用率每秒由 `nvidia-smi` 采样，突发计算可能导致均值偏低。

| 并发直播 | 输入队列丢帧率/路 | 末尾积压/路 | GPU 利用率均值/峰值 | 显存峰值 | 结论 |
|---:|---:|---:|---:|---:|---|
| 3 路 | 7.5%–7.6% | 0.80–0.87 秒 | 26.8% / 100% | 26,015 MiB（56.5%） | 不达标 |
| 5 路 | 36.9%–38.1% | 1.07–1.20 秒 | 45.8% / 100% | 43,359 MiB（94.1%） | 不达标 |

这些数字衡量的是**整个 ECS 规格与当前程序的组合**，不能单凭 GPU 利用率判断瓶颈一定在显卡；CPU 解码、内存带宽、推流和进程调度也可能参与。45 秒不足以证明长时间稳定运行，但足以显示这两档并发在当前设置下已经丢帧。

## 同日追加：同进程共享模型调度短测

同机推流的交叉对照也未通过：16 帧批次下，3 路各丢约 26%，5 路各丢约 50%；4 帧批次更差。移走推流编码后仍显著丢帧，因此**当前共享调度方案不能稳定承载 3–5 路**。显存充裕不等于还能接入更多直播；这次限制是包括解码、预处理、逐帧时序和推理调度的整条链路吞吐，不能仅凭平均 GPU 利用率把瓶颈归因于某一个环节。45 秒短测只足以否定这两档，不足以证明长期稳定性或确定最高可用路数。共享模式仍为默认关闭，现有单路路径不受影响。

## 第三轮：人物合批与更大球模型批次的云端复测

针对第二轮发现的「每路 16 帧、共享上限也是 16 帧」问题，实验性调度器现在允许独立设置球模型合批上限，并将兼容的人物检测请求合并成一次调用，仍按原顺序将输出分回各路。单路分析路径及默认关闭的开关不变。并发单元测试验证了三路各 16 帧可在上限 48 时合成一次球模型调用，以及人物请求合并后输出仍对应原路；这些测试**不代表实际吞吐提升**。

为了迅速筛选方向，本地 RTX 3050 Ti 上对同一冻结模型做了短调用测量（预热后 3 次中位数）。人物模型分别处理 4 帧与 12 帧耗时约 40.7 ms 和 87.2 ms，因此三次 4 帧调用合成一次 12 帧调用有潜在收益；球模型 4/8/12 帧分别约 115/614/1129 ms，大批次反而明显变慢。该笔记本只有 4 GiB 显存，不能将这些时延或最优批次外推到 L20。因此球模型共享上限仍默认为 16，较大批次只作为云端 A/B 参数；人物合批保留在可选共享模式里。

一次准备复测时，阿里云 `RunInstances` 因余额门槛拒绝创建，未产生 GPU 费用；临时网络已清理。账户补足后，第三轮在深圳另建一台相同的 `ecs.gn8is.2xlarge` L20 实例。仍由本地工作站模拟 1080p/30 fps 摄像头，经过业务 ZLM RTMP 供 GPU 订阅，分别测试三路和五路，各正式采样约 60 秒。两组都启用了人物检测合批；球模型共享上限分别为 16 与 48，每路仍积攒 16 帧后处理。判断标准是各路接近 30 fps、输入队列丢帧率低于 0.5%，且后半段不持续恶化。

| 球模型共享上限 | 同时直播 | 丢帧率/路 | 实际球检测帧率/路 | 后 30 秒丢帧率/路 | 显存峰值 / 峰值时剩余 | 结果 |
|---:|---:|---:|---:|---:|---:|---|
| 16 | 3 路 | 24.0%–25.2% | 22.3–22.8 fps | 19.9%–21.7% | 8,714 / 37,354 MiB | 未通过 |
| 16 | 5 路 | 44.7%–46.8% | 15.9–16.4 fps | 40.5%–47.4% | 9,180 / 36,888 MiB | 未通过 |
| 48 | 3 路 | 22.3%–23.4% | 22.9–23.2 fps | 20.2%–21.8% | 14,474 / 31,594 MiB | 未通过 |
| 48 | 5 路 | 43.4%–48.6% | 15.2–16.8 fps | 41.6%–47.0% | 25,548 / 20,520 MiB | 未通过 |

人物检测确实合并了请求，但没有消除丢帧。把球模型上限调到 48 时，实际平均每次调用只包含 16.1 帧（三路）或 21.4 帧（五路），因为各路到达时间并不总能对齐；显存占用却明显升高。后半段仍持续丢帧，排除了「只有开播瞬间掉帧」的解释。第一轮同机推流、第二轮异机推流、第三轮合批参数对照，均显示**这套完整算法在单台 L20 上不能稳定分析 3–5 路 1080p/30 fps 直播**。这不是 L20 芯片不可突破的理论上限；当前代码的解码、预处理、模型调用、人物检测、跟踪及事件处理共同决定吞吐，平均 GPU 利用率或空闲显存不能单独定位瓶颈。

第三轮首次执行的实验计时器曾在首批处理后抛错，使采集线程继续计数；该次无效数据已排除。修正后重跑的四组才进入上表，`profile_batches`、`detector_frames` 与模型调用统计均持续增长。原始逐秒数据在本地 `outputs/aliyun_l20_scheduler_v3/capacity_shared_16_fixed.json` 和 `capacity_shared_48_fixed.json`。实例于 08:05:57 UTC 创建、08:41:27 UTC 释放，按 ¥14.625104/小时估算实例与盘约 **¥8.65**，公网流量和实际账单另计。实例、安全组、交换机、测试 VPC 已删除；API 复查无遗留测试资源。

**部署建议：** 不要因为显存还有空余就向这台机器塞更多流，也不要未经测量就换一张更昂贵的单卡。当前可行的方向是把视频流分配给多个独立 GPU 工作进程/实例，先按每 GPU 一路做保守容量规划；已有 L40S 的单路高视角短测丢帧 0.10%，而单台 L40S 的五路测试同样失败。若成本要求每 GPU 两路，必须先在目标机型和高、平两类素材上做至少 90 秒的两路实测，再提高该上限。**本次没有测出 L20 的最高稳定路数**，因此不能承诺两路 L20 或单卡 L40S 足以覆盖所有视角。

## 追加瓶颈核查（未完成独立进程分段复测）

复核第三轮已经保存的云端 profiling：三路共享模型、每路 60 秒、共享球批次上限 16/48 时，每路累计墙钟时间分别约为球模型及热图解码 15.2/15.8 秒、人物检测 15.2/14.4 秒、跟踪 8.9/8.5 秒、事件判断 7.6/7.9 秒。系统 CPU 平均约 25%（8 vCPU），GPU 每秒采样均值约 27.8%/45.3%；三路丢帧仍为约 24.5%/22.7%。这些是**共享模式**数据，各阶段耗时不能直接相加来推断整机利用率，也不能替代独立进程的分段计时。它证明球模型、人物检测和时序处理均有明显成本，但未证明哪一个是独立进程三路丢帧的主因。

为定位独立进程三路的 7.5% 丢帧，准备了只在诊断包中生效的完整流程/跳过时序处理/跳过人物检测三组对照。新建的阿里云 L20 实例在拉取既有 9 GB 级 PyTorch 容器基础镜像时速度过慢，未在 32 分钟自动释放窗口内完成环境构建，**三组对照没有运行，不能从中得出性能结论**。诊断代码和资源日志位于被 Git 忽略的 `outputs/aliyun_l20_bottleneck/`；截至实验结束，API 已确认该实例、安全组和交换机均不存在。再次复测应先准备可在深圳快速拉取的预构建分析镜像，或使用已经装好依赖的实例，然后在相同 RTMP 输入下测三路独立进程的各阶段耗时和队列增长率。

10 分钟后中断/超时，Docker 保留已完成层后，第三次补拉在 3 分 44 秒完成。
默认 PyPI 下载在另一台临时实例上 10 分钟仍未结束；切换到阿里云 PyPI 镜像后，
完全相同的固定依赖在 3 分 37 秒内构建完成。这证明此前未运行消融实验的直接原因
是跨云镜像与公网依赖传输不稳定，不是本地代码包上传失败。

在成功构建的同一台 L20 上，用三个独立 Python 进程依次运行四组 35 秒短测。
由于 RTMP 发布端启动时间不同，每路实际收到约 10–27 秒源视频；因此本轮适合定位
阶段成本，不替代先前 45–60 秒容量测试，也不能单独证明长时间稳定。所有组都保持
三路、1080p/30 fps、16 帧球模型批次与每四帧人物检测不变。

5.52 ms。即球路径占已记录阶段时间约 44.2%，跟踪与事件合计约 48.0%，人物模型
约 7.5%。16 帧批次的球阶段平均 139.6 ms、P95 196.4 ms；跟踪平均 64.4 ms，
事件判断平均 89.3 ms。三进程 GPU 调用偶尔同时到达时，球模型峰值达到 100%；
之后每路还串行执行自己的跟踪和事件窗口，瞬时总耗时会逼近或超过 0.75 秒输入队列。

结论不是“L20 显存不够”：峰值只使用 54.1% 显存；也不是整机八核 CPU 已满：
CPU 中位数 28%、峰值 52.8%。人物模型不是当前优先项，关闭后吞吐没有稳定改善。
主要问题是**每路把 GPU 球推理、重复固定窗口的 CPU 跟踪和事件判断串行连接，三路
GPU 请求又会突发竞争**。球模型本身已接近三路实时边界，但单独运行仍接近 30 fps；
跟踪/事件消融带来的稳定改善更大。

下一步应先把跟踪和接触判断改为增量状态，避免每 16 帧重复计算八秒窗口；再用一个
公平的 GPU 推理队列维持 16 帧调用，同时让下一批 GPU 推理与上一批各路 CPU 后处理
重叠。每路仍保留独立跟踪、事件状态和 CPU 后处理。此前单进程共享模型方案降低显存
但把三路丢帧提高到 22%–25%，不能作为该流水调度的实现。完成流水改造后，再测球模型
FP16/编译优化是否需要作为第二阶段；仅凭空余显存增加并发不会解决当前问题。

`¥14.625104/小时` 的 API 报价估算实例与盘约 `¥6.48`，公网流量及最终账单另计。
此前两次环境准备失败也产生了短时实例费用。成功实例及两次失败实例的 ECS、

## 2026-09-27：增量时序实现与本地冻结候选回归

直播跟踪改为保留每路独立的因果前向状态。球的出生假设、活动 Kalman 状态、遮挡、
击球/反弹速度重置和已经终止的轨迹段只处理一次；每批仍从状态的只读副本生成带完整
前缀证据的平滑尾部。落点判断只计算新达到决策时限的帧，同时保留拟合半径与 NMS
邻域。旧八秒重算可用 `TENNISVISION_LIVE_INCREMENTAL_TEMPORAL=0` 回退。

首先用 1,737 帧冻结原生 RacketVision 候选逐批回放，保持 16 帧批次、八秒输出尾部、
人物框、球场映射、跟踪参数和落点阈值不变。旧实现的时序阶段耗时 61.224 秒；增量
实现耗时 18.433 秒，缩短 69.9%，即 3.32 倍。两者产生的 33 个直播落点帧逐帧完全
一致，没有漏掉或新增落点。独立合成回归还在每个批次把增量快照与从第一帧重新执行
的完整前缀比较，轨迹位置、真实观测、轨迹 ID、置信度、运动模式、终止原因及诊断
计数一致。该数字只衡量 CPU 跟踪与事件阶段，不代表包含 GPU 模型和 RTMP 的整条
直播吞吐；三至五路 L20 容量仍需使用新代码重新做云端端到端测量。

又对平视角缓存的前 2,700 帧（90 秒）执行同样的新旧直播回放。两条路径均输出
34 个落点，帧号逐个相同，无漏检或新增；旧时序耗时 72.735 秒，增量时序耗时
26.075 秒，缩短 64.1%，即 2.79 倍。对完整 6,982 帧平视角候选的跟踪核对中，
